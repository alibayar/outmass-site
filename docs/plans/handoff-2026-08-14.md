## The Stripe investigation — closed

The month-old question "why do we lose people at checkout" has an answer, from
all six `checkout.session.expired` payloads read in Workbench.

**The discriminator is not `payment_intent`** — it is null on every one of
them, because in subscription mode the charge rides the Invoice, not a session
PaymentIntent. It is the **customer / subscription / invoice triple**, which
Stripe only creates when the payment form is submitted.

| created (UTC) | who | card entered | Stripe branding shown |
|---|---|---|---|
| 07-16 22:23 | ekaynimos@hotmail.com (NL) | no | Metis Information Technologies Ltd |
| 07-29 13:44 | Kevin.McCann@mercedesscientific.com | **YES → declined** | Metis |
| 07-30 15:28 | marketing@mercedesscientific.com | no | Metis |
| 08-03 15:09 | Kevin.McCann@mercedesscientific.com | **YES → declined** | Metis |
| 08-10 07:14 | anbu.atomix@outlook.com (India) | no | Metis |
| 08-12 05:55 | flaviorfdc0406@outlook.com (Brazil) | no | **OutMass** |

**Four of five people opened the payment page and typed nothing.**
`customer_details.name/address/phone` are null on all four; the only populated
field is the email we pre-filled ourselves.

**Kevin is the only payments case.** Two attempts, two failures. 07-29:
MasterCard ••5683, Citibank N.A., decline code `transaction_not_allowed`; he
tried Link first and **Stripe's own risk engine blocked it**. 08-03: declined
by the issuing bank again. `transaction_not_allowed` means the card does not
permit this type of transaction — a corporate card with merchant controls, or
one closed to cross-border or recurring charges. Nothing on our side to fix.

**The descriptor hypothesis is dead, checked and wrong.** Stripe → Business
details shows trading name `OutMass` and statement descriptor `OUTMASS`
already. The bank saw a fine name.

**Five of six sessions showed "Metis Information Technologies Ltd"** on the
checkout page — the trading name was changed 08-11 and the payloads either
side bracket it exactly. Not the whole story: flaviorfdc0406 saw the corrected
name and still typed nothing.

### What it means

Every addressable loss is upstream of Stripe. Payments, pricing and Stripe
configuration have each been eliminated with evidence. **0.2.1 is aimed
exactly at the moment four of five people left**, and uploading it is the
highest-leverage single action available.

Also corrected: **tony@skylineprp.com is a paying customer**, not a lost lead.
He had an abandoned session from 07-20 and was wrongly counted in the earlier
"five people" list. Real list is five, and two of them are the same company
(mercedesscientific.com).

This diagnosis was only possible because `checkout_session_created` was added
on 07-20. Without it these five read as "clicked upgrade, then nothing".

## What shipped today (unpushed)

**Startup alerts name their service** (`09a4b08`). The guard added yesterday
fired within hours: a TEST Stripe key against the production database — the
exact condition it was written for, and its own docstring records the same
thing happening on the WORKER on 2026-08-10. It did not say WHICH service.
Railway variables are per-service; an alert that leaves you guessing is half
an alert. **Ali still has to find and fix that key** — see open actions.

**The success page tells the truth** (`b85ff2a`). `/billing/success` ignored
its own `session_id` and told everyone "your plan upgrade is now active". True
for a card in a second; false for a bank debit for days, while the account
sits on Free. Someone reading that, then seeing Free, pays again. It now reads
the session and says one of three true things, all non-settled paths carrying
"You don't need to pay again." Gated on `_SETTLED_PAYMENT_STATUSES`, the same
constant the webhook grants on, so a status Stripe invents later lands in the
cautious branch.

**One customer, one subscription** (`65b35f8`). Two routes, both closed.
(a) The webhook replay guard is single-slot — it asks only "is this the id
already on the row", so a *different* subscription reads as a first-time
activation and would overwrite the live one and re-zero quota mid-period. Now
it checks whether the stored one is still live in Stripe and, if so, writes
nothing and alerts with both ids. `_subscription_still_live` answers True when
it cannot tell, deliberately. (b) `create-checkout` swallowed a StripeError
into `sub = None`, which the status check read as "not subscribed" and opened
a second full-price session for an existing subscriber. Now 502s.

**Two ways a Microsoft connection died silently** (`03208ad`, closes #42).
(a) Microsoft ROTATES refresh tokens; the persist sat inside a try catching
only `httpx.HTTPError`, so a DB failure escaped into the caller's unguarded
per-contact loop with the new token unsaved and the old one spent. Now its own
try, returns the access token anyway, and alerts **only when the token was
actually rotated** — an unchanged one failing to persist costs nothing.
(b) A first sign-in returning no refresh token wrote no row and only logged.
The user has a JWT and a panel saying "connected" while every later token use
finds nothing. Now flags `requires_reauth` with reason
`no_refresh_token_on_first_signin` — the diagnostic whose absence is why #42
sat unanswerable.

**Three migrations** (`f0790d1`) — written, and **Ali ran all three**.
`cancel_at_period_end`, `month_reset_anchor_day`, `preferred_language`. The
029 verification query came back clean: no decayed anchors, so the backfill was
correct.

**Two quota defects** (`79398b6`). The anchor no longer decays — a 31st anchor
survives February instead of becoming a permanent 28th, and `next_reset_date`
uses the real day because that date is quoted to users in the quota-cap email.
And a subscription Stripe ends today no longer rolls over first: held for
**exactly one day**, so a lost `subscription.deleted` cannot strand someone at
zero quota forever.

**Ten email templates pinned** (`75b752a`). Every word of every transactional
email, subject/text/html, compared verbatim. This is the safety net under #36.

## #36 — where it actually stands

Blocked on nothing now; `preferred_language` exists. Three steps, in order:

1. **Move the ten templates to a single source.** Today they are inline string
   concatenation in four files, each duplicated by hand into text and HTML —
   translating as-is would mean 9 templates × 2 formats × 14 languages = 252
   bodies, and hand-duplicated pairs are the drift class this repo keeps
   getting bitten by. One body per template per language, HTML derived. The
   goldens prove the move changes nothing. **This is the next task and it was
   not started.**
2. **Capture the language.** `extension/i18n.js::getActiveLocale()` already
   computes the right value with the right precedence (Settings override →
   Chrome UI → navigator → en). Attach it to a call the panel already makes;
   no new endpoint, no version gate. Older builds never send it and the column
   stays NULL, which every template treats as English.
3. **Translate into 13 more languages.** Ali chose to do all of them rather
   than wait for usage data. Note the column will be empty for weeks either
   way, because filling it needs the extension to propagate through the store.

### Found while pinning them

**Five of ten send no `text/plain` part at all** — reconnect, account-deleted,
and all three inactivity tiers. Single-part HTML scores worse with spam filters
and renders as nothing in a text-only client. `HTML_ONLY` in the golden test
names them; deleting one from that set flips the check from documenting the gap
to defending the fix. Worth doing during step 1, since the refactor is already
touching every body.

## What today taught, beyond the fixes

The recurring shape held all day and turned up inside my own work twice.

- The mapping review found a guard I had just written was **already violated in
  latent form**: `send_email_task` could send mail charging no quota, was
  registered with Celery, and was one `send_task()` from live. Deleted.
- The sender-detection test I wrote to replace it **matched nothing at all**
  and passed clean — the real senders go through `async_post_with_retry`, not
  `.post()`. A check that silently matches nothing is the worst of the three
  outcomes, and only its own self-test caught it.
- The golden test's update flow was a `--flag` declared in a test file, which
  pytest silently ignores. It documented a workflow that did not exist.

Each was found by running the thing rather than reading it. The habit that
keeps paying: **check the thing whose failure would be silent, especially when
you wrote it.**
