## What went live

**CI had been blind for ten days.** `test_ai_language_contract.py` (added
2026-07-29) built an assertion message with a backslash inside an f-string
expression — legal from Python 3.12, a SyntaxError before it. Local dev runs
3.14; CI pins 3.11, so pytest raised at COLLECTION time and aborted the whole
job. **Zero backend tests ran in CI through the 0.1.27, 0.1.28 and 0.2.0
cuts.** Nothing shipped broken — the suites were run locally each time — but
there was no net under any of them. Two things worth keeping: a syntax error
in ONE test file silently disables every other one, and
`ast.parse(feature_version=(3,11))` does NOT detect this class (it accepts
the known-bad snippet on 3.14), so a checker built on it must self-test or it
reports a clean sweep it cannot see.

**Manual promo grants (migrations 026 + 027).** Gifting a plan by hand was
four UPDATEs from memory, one of them destructive: `expire_manual_promos`
skips anyone carrying `stripe_subscription_id`, so the column had to be
cleared for a promo to be expirable at all — and that column is the only link
to the customer's Stripe subscription. Now `grant_manual_promo(email, plan,
days, reason)` does the record and the plan change in one transaction, and
expiry restores exactly what the grant replaced.

**Delayed payments.** ACH Direct Debit was enabled, and
`checkout.session.completed` is not the payment for a bank debit — it is the
authorisation. The handler now withholds the plan until `payment_status` is
settled and grants on `async_payment_succeeded`; `async_payment_failed`
alerts an operator.

**An unknown Stripe price no longer becomes Pro.** Both plan lookups
defaulted to `"pro"`, so any price id not byte-identical to
`STRIPE_STARTER_PRICE_ID` delivered 10,000 emails a month for Starter money —
a second currency, an annual tier, or the new id that a price RISE mints.
Adding a price is a dashboard action, so the trigger sat entirely outside
code review, and the failure favours the customer so nobody would ever report
it.

**Sign-in failures now say whose problem they were.** Every failure carries
`attributed_to`: user, tenant, app, microsoft, or an honest unknown. The
settle fragment gained a second field, `mcode`, so a newer client can say the
same thing in the user's own language — 14 locales, translated and reviewed
per language.

**Test telemetry stopped polluting production.** Nineteen `ms_auth_failed`
events dated 08-06 carried `host=testserver` and payloads like
`<script>alert(1)</script>` and `😀💣` — the sanitizer probes from that day's
review, sitting in the production sign-in funnel for four days looking like
real users failing to sign in. conftest already blanked the API key, but that
guard lived in the TEST HARNESS, so a script driving the app through
TestClient outside pytest went straight through. The check is now in the code.

## The Faisal incident, and the lesson it earned

Read this before granting another promo.

A two-month Starter gift was granted on 08-08 at 11:48 UTC and was gone by
08-10. The customer had already been emailed that it was "already active".

Timeline:

| UTC | |
|---|---|
| 11:37 | the promo shield was **committed** |
| 11:48 | `grant_manual_promo` run — plan → starter |
| **17:17** | Stripe's final failed retry → subscription cancelled → `customer.subscription.deleted` |

Railway was still running the code from the previous push. The old,
unshielded handler wrote `plan='free'` and the gift evaporated. Every field
matched: `plan_updated_at` 17:17:54, `stripe_subscription_id` null,
`manual_promo_until` still set, grant row still `active`.

**Granting is a DATABASE write; keeping the grant alive is APPLICATION
behaviour.** The database was never wrong — the code meant to defend it was
not running yet. `grant_manual_promo` now says so in a RAISE NOTICE at the
moment someone grants.

Two more holes found while diagnosing it, neither the cause:

- **A chargeback was the last unshielded downgrade.**
  `_handle_dispute_created` wrote `plan='free'` unconditionally, so a dispute
  was the one remaining way to silently revoke a promise made in writing.
  Now shielded — the Stripe cancel still runs and the subscription id is
  still cleared, only the gift survives.
- **`grant_manual_promo` could gift a row at random.** It matches on email,
  and `users.email` has no unique constraint (only `microsoft_id` does). In
  PL/pgSQL `SELECT ... INTO` with several matches does not raise — it takes
  an arbitrary row. Migration 027 counts first. Checked 08-11: no duplicate
  emails exist today, so it is preventive. The 08-08 review of 026 raised
  exactly this and the agent examining it died on a session limit; it took a
  different incident two days later to come back to it.

**Faisal now:** plan `starter`, grant `active`, expires **2026-10-07**,
`stripe_subscription_id` NULL so expiry will revert him correctly. His card
was not "declined" — his bank refused twice on 25 and 28 July and told Stripe
to stop, after which a default Radar rule blocked seven more attempts. That
card is dead for us; he needs another method. **He is on 0.2.0 and has not
yet uploaded an Arabic CSV** — whether the decoder fix actually solves his
problem is still unknown. Watch for `recipients_uploaded` vs
`csv_upload_failed` on his next session.

## Railway environment variables — three incidents, one cause

Variables are **per-service**, and the backend runs three services from one
codebase (`backend/Procfile`: web, worker, beat). Every variable has to be
set three times and the failures are silent.

1. `TELEGRAM_*` on web only — operator alerts never fired from workers.
2. `INACTIVITY_NUDGE_ENABLED` on web only. Beat scheduled the task, worker
   executed it, worker read the flag as False. The nudges returned
   `skipped: disabled` every night for as long as the flag had been "on" —
   one paying customer sat four days past the 30-day threshold with an empty
   stamp and nobody knew.
3. `BACKEND_URL` still the railway.app host on the worker while web was on
   `api.getoutmass.com`. **The worker sends scheduled campaigns and
   follow-ups**, so their tracking pixels, click links and UNSUBSCRIBE links
   pointed at a shared-platform domain that corporate filters and the GFW
   block wholesale — the exact failure class the custom domain was bought to
   remove, this time landing on the customer's recipients rather than on our
   users.

The durable fix is task #37: project-level shared variables, referenced by
all three services. Copying by hand produced all three incidents.

Note when auditing: the three services run the same `config.py`. A variable
web needs and worker does not is not a real category — any difference is a
finding.

## Lessons this session earned

- **Deploy order is part of the change.** A database-level gift depends on
  application-level protection being live. Twice tonight the same shape
  appeared: migration run before code deployed, flag flipped before template
  deployed. Ask "is the code that defends this actually running?"
- **Mutation-test every guard, including the new ones.** Three guards written
  today were dead on first run: the unit tests proved the resolver correct
  and said nothing about whether any call site used it. Four end-to-end tests
  fixed it.
- **A test can encode the bug.** Three fixtures asserted `plan == "pro"` for
  a made-up price id, two asserted the old nudge copy, one asserted
  `meaning == "unclassified"`. Inverting them is better than deleting them —
  the new decision gets defended too.
- **Check the harness before believing the result.** A DNS check reported the
  MailerSend DKIM missing; the record was fine and the script was reading
  `.Strings[0]` off a CNAME. Same class as the benchmark that libelled
  charset-normalizer on 08-08.
- **The copy is part of the fix.** The nudge asked nobody why they left, told
  people to reinstall something they still had, pointed Edge users at the
  Chrome store, and promised personal outreach from a one-person team. None
  of that is code.
