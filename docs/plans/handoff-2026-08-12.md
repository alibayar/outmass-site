## The biggest finding: where users actually leave

Client-side, `oauth_failed` splits by `properties.code`:
`consent_declined` = 62 events across **34 people**, still happening;
`auth_page_failed` = 22 across 7, last seen 07-29 and effectively cured by
the warm-backend retry.

Chrome's "consent_declined" does NOT mean the user pressed No — background.js
labels any auth window closed without a successful redirect that way.

The decisive comparison: 34 people hit that client-side, and `ms_auth_failed`
on the server records only **11 unique people** across all meanings. So most
of the 34 never reached our backend — they closed Microsoft's window before
Microsoft redirected back. That is abandonment at Microsoft's own consent
screen, not a tenant block and not our error page.

Two consequences:

- The first-sign-in consent explainer shipped in 0.2.1 is aimed at exactly
  the right moment — it is the last thing read before that screen.
- **#24 is the lever, not a chore.** "Read your mail" is the most alarming
  line on that consent screen, and dropping Mail.Read from the first ask is
  the largest available change to what those 34 people saw. It is blocked on
  Edge publishing 0.2.0, because the replies-off banner is its prerequisite
  and shipped in 0.2.0 (commit 9df23d5). Flipping the server-side flag while
  Edge serves 0.1.26 would silently degrade every Edge user.

Caveat: small numbers, and the server-side `unclassified` bucket is 44 events
from only 3 people — concentrated noise. The 34-vs-11 comparison is the sound
part.

## sidebar_opened was lying, and the fix was already in the tree

`sidebar_opened` and `onboarding_step_viewed` both fire from one `init()`
in sidebar.js, yet PostHog showed 3 people vs 18 for 0.1.26. Impossible —
and onboarding fires only on FIRST run, so it should be the rarer one.

Cause: `_phEnqueue` was an unserialized read-modify-write over
chrome.storage. Two concurrent `track()` calls both read the same queue, both
wrote their own single-element version, last writer wins. `sidebar_opened`
fires microseconds before `compose_view_seen` in the same block, so it was
clobbered nearly every time. Loss is probabilistic and inversely
proportional to the gap — `login`→`oauth_completed` are ~100ms apart and
mostly survived.

**Already fixed**: commit 3cb2bbd (08-06, shipped 0.1.28) added the
`_phEnqueueChain` serialization while fixing the `oauth_completed`/`$identify`
version of the same race. Nobody noticed it also fixed this. Regression test:
`extension/tests/analytics-race.test.js`.

Consequence that outlives the fix: **any funnel figure computed from
pre-0.1.28 data understates the earlier event of every tight pair.**
Trustworthy data starts 2026-08-08.

## The 0.2.1 release review

Five independent lenses, two skeptics each, sixteen agents. Every finding
survived both skeptics — unusual, and the reason is that four of them were
introduced by this session's own work. All four fixed in a319e0f,
mutation-tested.

- **A quota-write failure could email a recipient twice.** The batch charge
  added hours earlier sat inside the per-contact `try` whose `except` calls
  `mark_failed(..., "deferred")` — after `mark_sent` had committed. Each
  charge now has its own try; so does the end-of-loop flush, which runs per
  campaign inside the beat's loop and would otherwise abort every remaining
  campaign. Both worker files were also missing a module-level logger.
  Plus the guard that closes the class at the single point all four send
  loops funnel through: `mark_failed` now carries `.neq("status", "sent")`.
- **A/B campaigns never resumed** while the release shipped a note promising
  they would. `evaluate_ab_tests` writes `failed_auth` to `ab_tests` AND the
  campaign row; `reauth_resume` knew about two tables. A/B rows are judged on
  `created_at` because a send-now campaign's `scheduled_for` is NULL, and go
  back to `awaiting_winner`, not `sent`.
- **Reconnect resumed campaigns the user had archived.** Archive is the ONLY
  control on a paused row — there is no cancel-campaign endpoint.
- **The panel promised a resume the backend refuses.** Rewritten in all 14
  locales to promise only the sign-in, not the outcome.

Not fixed, deliberately: **the ACH double-activation window.** During the
delayed-payment limbo the user is on `free` with no subscription id, and
`/billing/success` tells them the upgrade is active, so they can pay again by
card and end up with two subscriptions — after which the replay guard fails
to recognise the second activation and re-zeroes quota mid-period. Pre-dates
this diff (ACH was enabled 08-08). Needs a `/billing/success` change; not
something to squeeze into a release cut.

## Substring matching cost us four times in one day

Worth its own heading because the same mistake produced four different
failures, and the fourth shipped an incomplete feature rather than a merely
vacuous test.

1. `terms.html` quota guard: `"50 emails per month"` matched inside the
   CORRECTED `"250 emails per month"`, so the test failed on the very fix it
   protected.
2. Startup-guard test: asserted `"run_startup_checks()" in src`; commenting
   the call out leaves the substring in place, so the one mutation it existed
   to catch sailed through. Replaced with an `ast` parse.
3. Manifest permissions guard: `example.com` counted as "used" because
   sidebar.js ships sample CSV rows containing `john@example.com`. An email
   address is not an endpoint.
4. **`grep -v test`** — meant to drop test FILES — silently removed
   `ab_test["campaign_id"], {"status": "failed_auth"}` from a grep for the
   `failed_auth` write sites. Four lines came back instead of five, and
   `reauth_resume.py` shipped believing there were two write sites. That is
   the A/B bug above.

The pattern: grepping for a string in a file where that string can appear for
an unrelated reason. Every guard built on one now carries a self-test proving
it distinguishes the real case from the lookalike.

## The checkout step is where the money is lost, not the product step

Traced 08-13 after a cancellation. Two people reached Stripe Checkout in the
first half of August and left **without entering a card** — neither appears
in Stripe's transaction list at all: `flaviorfdc0406@outlook.com` (08-12) and
`anbu.atomix@outlook.com` (08-10, expired 24h later). Kevin.McCann is the
opposite case and needs a different answer: he tried twice and his bank
declined.

Cause, verified in the code: the Account tab had one "Upgrade Plan" button
that called CREATE_CHECKOUT with a hardcoded `starter` and opened Stripe. The
price was invisible until the payment form, and **Pro could not be bought
from the panel at all**. A control reading "show me the plans" that behaves
like "pay now" produces exactly this.

It also explains who stayed: Mary Bass clicked Upgrade EIGHT SECONDS after
signing in and paid. The button converted the already-convinced and lost
everyone who wanted information first.

Fixed in 412b50a — both plans listed with price and limit, price from Stripe
and limit from config.py, no number written in code or in any of the 42 new
locale strings. `upgrade_button_clicked` now carries which plan.

Still open: **nothing reaches the customer when a checkout is abandoned.**
The expired-session branch emits a PostHog event and a log line; no email, no
operator alert. Four warm leads have gone unanswered (Kevin ×2, Morgan,
anbu, flavio). A Telegram alert on abandonment is the cheap half; a customer
email needs a decision on tone.

## Lessons this session earned

- **A review finding is a hypothesis until you trace it yourself.** Sixteen
  agents, every finding surviving both skeptics — and it was still right to
  re-verify all four by hand before touching code. Two of the four needed
  their scope corrected in the process.
- **Fixing a class means fixing it where all callers funnel.** The quota bug
  had four call sites; the durable fix was one `.neq("status", "sent")` in
  `mark_failed`, not four try blocks.
- **A test that measures nothing passes.** The panel overflow guard measured
  an empty Reports list, then an unrendered one, then a 1280px viewport of a
  380px panel — three ways to be green while looking at the wrong thing.
- **Keys are the worst case, real strings are the true case.** The English
  suite renders i18n KEYS, so it reports overflows users never see and misses
  the one that matters — `#btn-delete-template` overflowed by 32px in FRENCH
  and fitted in English.
- **Do not put a promise in the product the code does not keep.** Argued
  twice in one evening, then written into a panel note anyway.
