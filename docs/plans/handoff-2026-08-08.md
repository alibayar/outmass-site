## The CSV decoder, which took three rewrites and four reviews

Worth reading before touching `decodeCsvBuffer` again, because each rewrite
looked correct to me and each shipped a silent-corruption path.

**The rule it now follows, without exception: never use a decoder whose
output cannot be checked.** And the only check that ever worked is that
**real writing comes in RUNS** — names and words are two or more characters
of the same script side by side, while a diacritic misread through the wrong
table stands alone between ASCII letters.

Measured 2026-08-08:

| | non-ASCII | inScript | longest run |
|---|---|---|---|
| real Russian (cp1251) | 43.1% | 100% | **8** |
| real Greek (cp1253) | 48.7% | 100% | **12** |
| real Chinese (gbk) | 7.7% | 100% | **2** |
| diluted GBK, 2 CJK names | 0.9% | 100% | **2** |
| Polish read as cp1251 | 6.1% | 100% | **1** |
| German read as cp1251 | 8.1% | 100% | **1** |
| Polish read as gb18030 | 5.8% | 83% | **1** |

Note what the first two columns do NOT do. `inScript` is 100% on both sides.
And a volume threshold is wrong in **both directions at once** — it accepts
Polish at 6.1% while rejecting the real Chinese list at 0.9%. Three separate
guards were built on those columns and all three had to come out.

**What each rewrite got wrong:**

1. Latin codepages as a terminal catch-all → `Ayşe Yılmaz` became
   `Ayþe Yýlmaz`, reported as a clean success. Also `shift_jis`/`euc-kr`
   ahead of gb18030 stole Chinese files from ja/ko users.
2. Accept-Language as evidence → one `ru` anywhere in that list put
   windows-1251 in the chain, where it claimed a German list. And the
   "two scripts fit → reject" rule was written as `continue`, so it fell
   through to gb18030 and returned Chinese mojibake instead of rejecting.
3. `gb18030` itself was an unguarded catch-all **and had been since 0.1.24** —
   not mojibake but DATA LOSS: it pairs a single high byte with the following
   ASCII letter, so `Łukasz` decoded to `kasz`, the `u` eaten.

**Now:** UTF-8 → the codepage the user's own language names (script tables
only, run-gated) → gb18030/big5 (run-gated) → refuse. No Latin codepage is
ever chosen automatically. Accept-Language is not consulted.

## The picker, and why the preview is the whole feature

Refusing is safe but it is a dead end, and both documented churn cases died
in it. The information needed to choose is not in the bytes — it is in the
user's head. So the dialog asks, and shows decoded rows that re-render live.

Two things the review caught that would have made it theatre:

- **It rendered columns 0 and 1.** In a file laid out `id,email,name,company`
  the names are at index 2 and the first two columns are pure ASCII, which
  decodes identically under all 14 options. The preview was pixel-identical
  for every choice with the confirm button lit. It now selects the cells that
  actually carry non-ASCII, and disables the button when the visible sample
  has none.
- **A late suggestion could repaint a different file.** One DOM element set,
  per-upload closures; the staleness guard asked "is a dialog open", not "is
  MY dialog open". Cancel on file A, open file B, A's response lands → A's
  rows in B's preview, and Use this decodes B with A's label. Fixed with a
  generation ticket.

Options are **endonyms** (Polski, Türkçe, Русский, 日本語) — no translation
needed, correct in every locale, and what a person actually scans for.

## Detection: measured, not argued

51-file corpus, 12 languages, real (60-row) and short (3-row) sizes:

| | correct | refused | **wrong** |
|---|---|---|---|
| our rules | 40 | 9 | **2** |
| charset-normalizer | 42 | 0 | **9** |
| jschardet | 38 | 0 | **13** |

Global accuracy is the wrong number — we only ever ASK about files our own
rules refuse. On those 9: **charset-normalizer 8, jschardet 3**.

**jschardet is out**, and the review found the reason: v3.1.4 has **no Arabic
and no Turkish model at all** — its supported set omits windows-1256, 1254,
1257, 1258, inherited from Mozilla's chardet. Where it does answer it says
windows-1252 at **0.95 confidence** for a Turkish list. 334 KB and LGPL-2.1+
were never the main objection.

**charset-normalizer may never decide unsupervised.** Its own confidence does
not separate its right answers from its wrong ones — chaos 0.0 appears in
both sets — and it calls a Russian list `x-mac-cyrillic`. It pre-selects the
dropdown and nothing more.

## Lessons this session actually earned

- **Mutation-test every guard.** Two assertions I wrote were DEAD: one regex
  matched a different line in the same file, another let a truthy check pass.
  Both looked right and both were green.
- **A test that passes for the wrong reason is worse than no test.** The
  ambiguity assertion was `!encoding.startsWith("windows-")`, which
  `gb18030` satisfies — so it passed while producing exactly the mojibake it
  existed to prevent.
- **Check the harness before believing the benchmark.** Three separate
  versions of my own comparison scored *correct* answers as failures because
  I fed Python codec names (`utf_8`, `cp932`) to `TextDecoder`. The first
  table libelled charset-normalizer on 24 of 51 files.
- **Claims follow the product, including between commits.** The changelog was
  wrong three times in one day — once announcing a permission change gated
  behind an unflipped env var, once promising a refusal the picker had just
  replaced, once describing behaviour a later commit changed.
- **A documented trade-off stops being acceptable the moment you promise the
  opposite in print.** The Cyrillic-claims-Latin collision was fine while it
  was a code comment and a blocker once the changelog said we would rather
  refuse than guess.
