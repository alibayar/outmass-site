## Incidents resolved this session (all root-caused with evidence)

**1. Rage-uninstall, 2026-08-03 ("GARBAGE. DOES NOT WORK").** A US user with a
447→462-recipient list installed, onboarded, uploaded, and then clicked Sign in
SIX times over three hours with nothing happening, got not_authenticated on
every send, and uninstalled 29 seconds after the last dead click. Cause: the
single-flight OAuth guard. A `launchWebAuthFlow` that never settles keeps the
MV3 service worker alive, so the in-memory flight entry survived forever and
every later click joined a promise that would never resolve. Railway logs
confirmed exactly one `/auth/login` at 18:36:56 and none at any of the six
later click times. Fixed in 0.1.27: three-tier behaviour (<10s silent join,
first re-click <1min gets a localized "the window is already open, check your
other windows" hint, any click after the hint or after 1min opens a FRESH
window), plus a 5-minute hard timeout so sidebar buttons can never brick.

**2. Payment-failure alerts were never arriving.** Three Stripe failures
(07-29 ×2 for a new customer's declined first purchase, 07-30 for a renewal)
produced no Telegram. Root cause proven by `users.plan_updated_at`: the
handler writes it on every run and it still read 2026-07-25, so the handler
never executed — **the endpoint was not subscribed to
`invoice.payment_failed`**. Ali added it (plus `payment_action_required` and
`payment_succeeded`, both of which now have handlers). Verified live: Kevin's
08-03 failure produced the alert.

Four defects in that one path, all fixed: the event was not subscribed; the
alert text said "Stripe will auto-retry" for FIRST payments (it does not —
Stripe voids the invoice and the subscription expires ~24h later, which cost
a sale on 07-29); it reported "User: unresolved" for first-time buyers
(stripe_customer_id is only learned at checkout.session.completed — now read
from the invoice); and `_telegram_alert` returned silently when config was
missing, so an entire channel could be dead for days. Now: dropped alerts log
at ERROR with the alert body, `GET /` reports `alerts: true|false`, and the
daily report asks the web service and prints "🔕 ALERTS OFF on web" if it is
not configured (the worker's own ability to send proves nothing about web —
Railway environments are per-service).

**3. `consent_declined` was lying to us.** 24 of 26 sign-in failures carried
that one label, which is Chrome's wording for "auth window closed without a
redirect" — NOT "the user pressed No". When Microsoft rejects a sign-in it
redirects to `/auth/callback` with the real cause (AADSTS90094 admin approval,
AADSTS50020 wrong tenant, …), and the callback rendered an error page and
dropped it; the user then sits on OUR error page until they close the window,
and Chrome reports "did not approve". So tenant blocks were filed as user
refusals. Now `/auth/callback` reports `ms_auth_failed` with the AADSTS code
(never the raw description — it embeds the user's address, tenant and object
ids), `/auth/login` reports `ms_auth_window_opened` as a funnel midpoint, and
oauth_started/failed carry seconds-in-window, attempt_no and an opaque
attempt_id that joins the client funnel to the server events.
