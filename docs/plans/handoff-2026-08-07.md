## Today's three findings (2026-08-07), all with evidence

**1. We re-prompt users who just declined. Our bug.** A US user installed and
clicked sign-in 48 seconds later — highly motivated — then tried SIX times
over 75 minutes and left. The sequence:

```
07:19:43  ms_auth_failed  AADSTS65004 = user_declined_consent
07:19:42  oauth_retry     (client saw "auth page could not be loaded")
07:19:45  ms_auth_window_opened   ← a fresh consent screen
```

Mechanism: `_error_page` returns **HTTP 400**. Chrome reports that as
"Authorization page could not be loaded", which matches the client's
`auth_page_failed` branch, which fires our one-shot auto-retry. The code
comment right above it says *"Never retry consent declines: that's a
user/tenant decision, and reopening the window would only annoy"* — the
intent was right, but a decline reaches us disguised as a page-load failure,
so the guard never engages. **Fix: return 200 instead of 400** (auth.py
`_error_page`, ~line 1015). The 9s settle-redirect then does its job cleanly.

**2. First hard proof that users actively decline.** AADSTS65004 is
Microsoft's "user declined to consent" — not a tenant block, not admin
approval. Twice today. This converts the day's hypothesis into evidence: the
permission list itself is what loses first-timers, which is exactly what the
Mail.Read split was built for. (Yesterday's 45 `ms_auth_failed` events were
synthetic probes from my own review agents — distinct_id
`anonymous_auth_failure`, dated 08-06 — exclude them.)

**3. A Polish user was lost by our CSV decoder.** They installed, reached the
panel, completed onboarding, then:
```
09:53:15  csv_upload_failed  invalid_encoding
09:58:17  oauth_failed       auth_timeout 300s
```
`decodeCsvBuffer` (sidebar.js ~line 676) tries only **utf-8, gb18030,
big5**. The Chinese codepages were added after the 2026-07-14 zh-CN churn;
no European ones exist. A Polish Excel CSV is windows-1250 and fails all
three. Same bug class, different continent. **Fix: add windows-1250/1252/
1251/1254 to the candidate list, ordered by UI language.** The existing
`csv-decode` suite already has cp125x fixtures to test against.

## Other things worth doing (proposals, none approved)

Ordered by my estimate of value per unit of work.

1. **Check what the Microsoft consent screen actually SAYS.** Publisher
   verification was done 2026-06-24 against `metisbilisim.com`. So a user who
   installed "OutMass" may be shown "Metis Bilişim" as the verified publisher.
   If the name on the consent screen does not match the product they just
   installed, declining is a rational response — and it would explain
   AADSTS65004 better than the scope list does. **Ali: Azure → App
   registrations → OutMass → Branding & properties — what are the display
   name and publisher shown?** 30 seconds, potentially the largest single
   explanation we have.
2. **The sidebar has no consent explainer.** `popupConsentExplainer`
   ("Microsoft will ask permission for OutMass to send emails… we never store
   your email content") exists ONLY in popup.html. The sidebar is the larger
   sign-in path. Priming before the ask is a known lever against declines and
   the text already exists in 14 locales.
3. **Defer sign-in until the first send.** The structural version of the
   activation problem: today the panel is useless signed out, so we ask for
   mail permissions before the user has experienced anything. Letting them
   upload a CSV, compose and preview signed out — and asking for consent at
   the moment they press Send — moves the ask to after they have invested
   effort and can see why we need it. Big change, biggest potential payoff.
4. **After N failed attempts, offer help.** Today attempt 6 looks identical to
   attempt 1. A "having trouble?" line with support@getoutmass.com after the
   second failure costs nothing and catches exactly the 6-attempt user above.
5. **Locale gap.** No Polish, Italian, Dutch or Korean. Today's Polish user
   read every error message in English, including the CSV one that was
   supposed to help them.
6. **Plan the Mail.Read measurement before flipping.** The flip's success
   metric is the decline rate (`ms_auth_failed` with AADSTS65004 + client
   `consent_declined`) per sign-in attempt, before vs after. Write the query
   first; at ~60 installs/month the sample takes weeks and we must not
   re-litigate it from memory.
7. **Root logger config.** No `basicConfig` anywhere, so every `logger.info`
   in the backend is invisible in Railway — including reply_detector's "user
   lacks Mail.Read scope". One line in main.py, but it changes production log
   volume, so it needs Ali's nod.

## Open decisions (Ali's)

  (a) no interlock between the env flag and migration 024; flipping first is
  a permanent lockout plus a reauth-email loop, (b) narrow users have no
  in-product recovery path, plus two silent regressions — follow-ups chasing
  people who already replied, and reply_rate reported as 0.0%.
- `past_due` → instant downgrade (one `elif`; revenue decision, hit Faisal).
- Auto-resume multi-cycle drain needs a `campaigns.updated_at` column.
- `graph_api.js` is fully dead code (its three message types are sent by
  nothing). Removing it drops `graph.microsoft.com` and
  `login.microsoftonline.com` from host_permissions — good hygiene, but it
  will NOT shorten the browser's permission sentence (6 hosts still reads as
  "a number of websites").
